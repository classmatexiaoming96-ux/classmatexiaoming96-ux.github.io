AI 软件工厂实战：把 Codex 与 Claude Code 放进工程流水线

I Built an Agentic Software Factory with Codex and Claude Code

一、问题引入：软件工厂不是再买一个聊天机器人

这个视频讨论的不是“让 AI 写更多代码”这么简单的事。Owain Lewis 把焦点放在工程系统本身：一个需求从想法、ticket、设计、拆解、实现、测试、review 到合并，原本就是一条流程；所谓 AI 软件工厂，是把 agent 放进这条流程里，让它承接那些可以被规范化、验证和重复执行的环节。

视频一开场就回应了一个常见质疑：网上关于 AI software factory 的说法很多，听上去像概念营销。但作者的结论更朴素：它真正有价值的地方不是把人完全拿掉，而是把已经存在的工程活动变成更清晰的输入、步骤和检查点。换句话说，Agent 的效果上限很大程度取决于团队有没有把工作说清楚。

这也是本视频适合开发者看的原因。它没有把 Codex、Claude Code、Factory 或 Docker sandbox 当成魔法，而是把它们拆回工程语言：队列、规格、验收条件、任务分解、执行器、代码审查、权限隔离和合并策略。

二、核心概念解释：把开发流程变成可交给 Agent 的接口

1. Intent：需求入口不能是含糊愿望

作者先把传统开发流程抽象成 intent。这个 intent 可能来自客户问题、PM、stakeholder，也可能来自开发者自己的想法。进入 AI 软件工厂之前，它需要被转成一个可处理的工作项，而不是一句“帮我优化一下系统”。

对 Agent 来说，最危险的输入不是复杂，而是不明确。一个含糊需求会让模型自己补上下文、自己假设边界、自己决定验收标准；在个人 demo 里这可能看起来很快，在团队工程里就会变成不可追责的随机输出。

2. Spec：先设计，再执行

视频里反复强调的核心动作是 planning and design。作者展示了一个非常简单的 plan skill：把 brief 或 spec 转成结构化 ticket，包含 outcome、context、acceptance criteria 以及 agent 完成任务所需的其他信息。这个步骤看似普通，却是 AI 软件工厂能稳定运行的基础。

这里的关键不是模板有多复杂，而是团队是否愿意把“为什么做、做什么、怎么算完成”写出来。AI 工具越强，越不能跳过这一步，因为模型很擅长填空，也很容易填错空。

3. Worker：Agent 是执行单元，不是唯一决策者

在作者的流程里，Claude Code、Codex、Pi 等工具都可以作为 worker。视频给出的观点是：具体用哪个 Agent 没有大家想象得那么决定性，真正决定效果的是 workflow。也就是说，Agent 是流水线里的执行器，而不是流程本身。

这个判断对工程团队很实用。不要把能力建设押注在某个模型的 UI 上，而应该沉淀可以迁移的工作契约：ticket 格式、上下文包、代码检查、测试门禁、review 规则、合并策略。模型可以替换，流程资产应该留下。

三、关键论点与实操步骤：从手工工厂到自动化工厂

手工软件工厂：先让单个 ticket 可交付

视频前半段展示的是“手工工厂”流程：人负责写清设计和计划，然后把实现任务交给 Agent。Agent 在独立上下文里完成代码、测试和 PR，最后由人或另一个 Agent review。作者说自己现在大多数开发工作都采用这种方式：把时间花在规划和设计上，实际实现时交给 Agent。

这个阶段的价值是训练团队写好任务。不要急着做全自动化，先确认一个 ticket 在无人陪跑的情况下能被 Agent 完成、能被测试证明、能被 review 接住。只有这个最小闭环稳定，后面的队列化、批处理和自动合并才有意义。

自动化软件工厂：Factory 编排 intake、refine、build、test、review、merge

后半段作者展示了自己用 Rust 写的开源项目 Factory。它把软件工厂的想法编码成一个可运行系统：从 intake 拿到 idea，经过 agent 生成 specification 和 task，再进入 build、testing、review，最后等待 merge。人不再逐步敲命令，而是在任务板上协调状态。

这并不意味着系统可以无限信任。相反，越自动化越需要明确的状态机。一个 ticket 什么时候可以进入 build？测试失败后应该回到哪个状态？review 是人看、Agent 看，还是两者都看？这些问题如果不在流程中定义，自动化只会把混乱放大。

Sandbox：自动化之前先限制破坏半径

作者专门讲了 sandboxing。视频里的说法很直接：如果要在生产或团队环境中运行这类系统，就必须小心 worker 的权限。作者本地常用 Git worktree，团队或 VM 环境则倾向 Docker sandbox、普通容器或其他隔离方案。

这点值得单独拎出来，因为很多 AI 编码流程失败不是模型不会写代码，而是执行环境没有边界。Agent 需要读仓库、安装依赖、运行测试、改文件、提交补丁，但它不应该默认拥有破坏数据库、删除共享目录、污染主分支或泄露凭据的能力。

成本：确定性轮询，只有真正开工时才花 token

视频也回应了成本问题。作者认为，一个设计良好的工厂系统不应该每秒都调用模型。Factory 的思路是大部分时间用确定性代码轮询 GitHub 或任务队列；只有发现真实工作项时，才启动 Agent 消耗 token。

这个设计让成本从“持续燃烧”变成“按工作触发”。对企业团队来说，这比单纯问某个模型每月多少钱更重要：你需要知道 token 花在了什么 ticket 上，输出是否通过测试，失败是否可重试，是否能审计。

质量边界：AI 不够聪明的任务仍然需要人

作者没有把软件工厂描述成完全自治。他明确承认，有些任务不适合完全交给 Agent。架构判断、产品权衡、安全边界、复杂跨团队依赖，仍然需要工程师批判性思考。AI 工厂更适合机械性升级、清晰 bug fix、重复迁移、局部重构和已有标准下的实现。

这也是正确使用它的分界线：能写清验收条件、能自动或半自动验证、失败代价可控的任务，可以进入工厂；需要新战略、隐性业务判断或高风险生产操作的任务，需要人站在流程前面。

五、引用块：视频里最值得带走的判断

真正重要的不是你选择哪个 Agent，而是你有没有把工作流设计好。

这句话基本概括了整支视频。Claude Code、Codex 或 Pi 都只是执行器；能不能稳定交付，取决于需求是否被整理成可执行 ticket，环境是否被隔离，测试是否能给出反馈，review 是否能守住质量门槛。

AI 软件工厂更像 CI/CD 的下一步：把一致的工程流程套到 AI 编码任务上。

作者用 CI/CD 类比很准确。过去团队把部署从手工操作变成流水线，不是为了取消工程师，而是为了让每个人都走同一套可靠流程。AI 软件工厂也应该如此：它应该提升一致性，而不是让每个开发者各自发明 prompt 手艺。
