01问题引入 / 背景

这个视频不是在演示“让 AI 写一个小应用”这么简单。讲者先把上一集的 bookmark dashboard 作为对照：那一次，用户给 Claude Code 明确需求，Claude Code 负责实现；这一次，目标是让 Claude Code 从一句任务描述里自己拆步骤、提问题、查资料、整理证据并产出报告。换句话说，重点从“代码生成”转向“工作流自治”。

这类教程的价值在于它把 agentic workflow 拆成普通人能操作的几个抓手：VS Code 里的 Claude Code 面板、项目根目录的 CLAUDE.md、先计划再执行的 Plan Mode，以及用可复用工作流文件沉淀任务规则。对于刚开始用 coding agent 的人，真正的难点往往不是模型会不会写代码，而是怎样把目标、约束、验收标准和迭代方式说清楚。

核心判断可以转述为：不要把 agent 当成更长的聊天窗口；要把它当成会读项目上下文、会维护文件、会按计划推进的工作系统。

02核心概念解释

从 chat、build 到 agentic

视频用三层模型解释 AI 使用方式。第一层是 chat：问一句、答一句，适合解释概念或临时查询。第二层是 build：用户明确告诉 AI 要做什么，AI 负责写代码、改文件、生成页面。第三层才是 agentic：用户描述目标，AI 先制定计划，再选择工具、提出澄清问题，并在执行过程中处理偏差。

这个区分很关键。很多人以为“我让 AI 连续做十步”就是 agent，其实那仍然可能是用户在手动驱动流程。更接近 agentic 的模式是：你定义成功标准和边界，系统自己拆解“澄清问题、研究、综合、输出、修订”这些阶段，并在执行前把计划亮出来让你审查。

CLAUDE.md 是项目级 onboarding

讲者强调的 CLAUDE.md 可以理解为给 Agent 的入职文档。它不负责某一次提示词，而负责长期上下文：项目是什么、目标用户是谁、文件命名习惯是什么、输出格式怎么定、什么时候要先问问题。Claude Code 启动时会读这个文件，所以它比临时聊天里的补充说明更稳定。

在教程示例里，CLAUDE.md 被用来写清“你是研究助手”“在研究前询问范围、受众和我最关心的问题”“输出要有结构化报告和来源”。这让后续每次研究任务不必重新解释底层规范，用户只需要给一个主题，就能触发一套相对固定的工作方式。

Plan Mode 是执行前的制动器

Plan Mode 的作用不是让模型更慢，而是让它先把行动路径暴露出来。讲者在 VS Code 里切到计划模式后，只描述“我想给你一个主题，你研究、组织并输出报告”，Claude Code 立刻拆出澄清、研究、综合、写作、保存等阶段。用户可以接受、继续规划或补充约束。

这一步对初学者尤其重要。没有计划模式时，Agent 可能过早改文件、产出一堆不符合目标的内容；有了计划模式，用户可以先审查任务边界，补充“结尾要有行动建议”这样的要求，再允许它真正落地文件。

03关键论点 / 实操步骤

第一步：在 VS Code 里建立可观察的工作区

讲者选择在 VS Code 中完成教程，而不是只在终端里操作。原因很实际：文件浏览器能实时看到 Agent 创建了什么，Claude Code 面板能显示计划和执行过程，Markdown 文件可以直接预览。对于第一次构建 agent workflow 的人，可观察性比炫技更重要。

示例项目文件夹叫做 “my first agent”。它一开始几乎是空的，只先放入 CLAUDE.md。这个设计故意降低复杂度：先让学习者理解 Agent 如何根据项目说明组织工作，而不是被已有代码库、框架或部署问题干扰。

第二步：先写规则，再写任务

视频里最值得记住的顺序是：不要一上来就说“研究某个主题”。先写项目规则，让 Claude Code 知道自己是什么角色、应该怎样问问题、最终应该产出什么格式。讲者把 CLAUDE.md 比作新员工入职资料，这个比喻很准确，因为 Agent 的稳定性很大程度来自上下文制度，而不是单次提示词灵感。

一个可执行的 CLAUDE.md 至少要覆盖四件事：角色定位、工作步骤、输出格式和质量要求。比如“研究前先问清范围和受众”“报告要有 executive summary、background、key findings、sources”“结尾要给下一步行动建议”。这些规则越明确，Agent 越不容易生成泛泛而谈的内容。

第三步：用目标描述触发计划

在示例中，用户并没有列一套机械步骤，而是描述目标：“给一个主题，你要深入研究、组织发现并输出结构化报告；开始前问清范围、受众和特别想知道的问题。”Claude Code 的价值就在这里体现：它能把目标拆成阶段，还会主动提出质量检查。

这里的关键不是“提示词写得很长”，而是把任务中的决策权和检查点放对位置。用户保留目标和验收标准，Agent 负责路径设计；用户再审查计划，决定是否执行。这样既有自动化，也有控制力。

第四步：接受计划后观察文件级产出

当用户接受计划后，Agent 会创建研究报告 Markdown 文件。视频中讲者强调要看左侧文件浏览器，因为 Agent 创建、修改和保存的文件都会直接出现在项目中。这个细节让新手理解：Claude Code 不是只返回一段聊天内容，而是在工作区里形成可继续编辑的真实产物。

生成的报告包含主题、时间范围、受众、执行摘要、背景、关键发现和来源。随后，讲者又要求把执行摘要缩成三条，并增加一个“前五个 AI agent 工具”的对比表。Agent 没有从头重写，而是在已有报告里定位相关段落并做定向修改，这就是项目上下文带来的复利。

第五步：把一次成功变成可复用 workflow

视频后半段的隐含目标是把“研究报告”变成可重复执行的工作方式。一次 prompt 成功不等于 workflow 成功；只有当规则能放进 CLAUDE.md，输出结构能稳定复现，后续修改能基于已有文件迭代，才算真的进入 agentic 工作流。

讲者也提醒不要沉迷插件。内置文件读写、计划、提问和 Markdown 输出已经足够完成一个可靠的研究 Agent。额外工具应当服务于清晰流程，而不是替代流程设计。

05引用块 / 核心判断

“先计划，再执行”是本视频的主线。Plan Mode 让 Agent 在改文件前先交出路线图，用户可以在成本最低的时候纠偏。
CLAUDE.md 的价值不在于神秘语法，而在于把团队规则、输出格式和常见偏好写成项目级常识，让每次会话都从同一套上下文出发。

如果只看一个实践建议，就是把每个 Agent 任务拆成三份材料：项目说明、当前目标、验收标准。项目说明放进 CLAUDE.md，当前目标放进 prompt，验收标准在计划阶段确认。这样做比不断追加“再帮我改一下”更稳。
