把 Claude 用到专业级：从记忆、项目到 Co-work 和 Code

英文原题：Use Claude Better Than 99% of People (Beginner to Pro)

Futurepedia 16 分 15 秒 约 17,725 次观看 Claude · Projects · Skills · Co-work · Code

01问题引入：Claude 不是一个更会聊天的搜索框

这支视频解决的是一个很常见的问题：很多人买了 Claude，却仍然只把它当成“问一句、答一句”的聊天工具。这样当然能得到摘要、邮件草稿和临时建议，但远没有碰到 Claude 的真正上限。视频作者的主线很明确：Claude 的价值不只在模型回答质量，而在你能不能把记忆、项目、知识库、技能、连接器、Co-work 和 Code 组织成一个稳定的工作系统。

因此，这不是一支单纯的按钮介绍视频。它更像一份从个人使用到 Agentic 工作流的迁移路线图：先把上下文带进 Claude，再把任务放进 Projects，再把常用流程沉淀成 Skills，最后把长任务交给 Co-work，把开发任务交给 Claude Code。对已经熟悉 ChatGPT、Gemini 或其他 LLM 的用户来说，最值得看的地方在于“如何把旧有上下文迁移过来，并持续让 Claude 记住你真正的工作方式”。

核心判断可以概括为：不要把 Claude 当成一次性问答框，而要把它训练成理解你、能复用上下文、能接入工具、能承担长期任务的工作台。

02核心概念：从模型选择到上下文资产

先把“记忆”当成迁移成本来管理

视频一开始提到一个容易被忽视的点：用户不愿切换 AI 工具，往往不是因为新工具差，而是旧工具已经积累了很多关于自己的偏好、项目和表达方式。Claude 的记忆导入功能就是为了解决这个切换成本。作者建议在设置里找到 capabilities，把从 ChatGPT、Gemini 等工具导出的记忆内容粘贴回来，然后开启“搜索和引用历史聊天”以及“从聊天历史生成记忆”。

工程上可以把这件事理解成“初始化个人上下文层”。如果没有这层，Claude 每次都像第一次认识你；有了这层，它会慢慢知道你做什么项目、喜欢什么输出格式、常见约束是什么。注意这里不是让模型无限制地记住一切，而是把长期稳定的偏好和背景变成可复用资产。

模型和 effort level 是成本控制旋钮

作者强调模型下拉菜单不是装饰。Haiku 更快但能力较弱，Sonnet 在速度和质量之间更均衡，Opus 更适合复杂推理。另一个关键项是 effort level：简单改写、格式整理、短问答不需要最高努力级别；需要规划、分析、代码和策略判断时，才值得付出更多 token 与等待时间。

这条建议对日常使用很实际。很多人觉得 AI “贵”或“额度不够”，其实是把所有任务都交给最重模型和最高思考强度。更稳的做法是按任务风险分层：低风险任务用快模型，中等任务用 Sonnet，关键判断或复杂构建再切到更强配置。

Projects、Knowledge 和 Skills 是三个不同层次

Projects 解决的是“把相关聊天和资料放在同一个工作区”；Knowledge 解决的是“把文件、指南、品牌资料、产品说明放进上下文”；Skills 解决的是“把一套可重复执行的流程打包起来”。它们看起来都在提供上下文，但用途不同：Project 是容器，Knowledge 是资料库，Skill 是操作手册。

视频中用“周末特价菜内容包”的例子解释 Skills：上传菜单、设定输出风格，让 Claude 每次都按固定流程产出网站文案、社交帖、图片提示词和邮件内容。这个例子说明，Skill 不只是提示词收藏，而是把“我每周都会做的一组动作”变成可复用工作流。

03关键论点与实操步骤

第一步：把旧上下文迁移进 Claude

如果你已经长期使用另一个 LLM，先不要急着重新训练 Claude。视频建议先从设置里导入其他 AI 提供商的记忆：复制 Claude 给出的提示词，到原工具中生成一份个人上下文摘要，再粘回 Claude 并加入记忆。这个过程虽然简单，但意义很大，因为它能让 Claude 一开始就知道你的工作背景、语气偏好和常见任务。

导入之后，还要开启历史聊天引用和自动生成记忆。否则你只是做了一次静态导入，后续不会持续沉淀。更好的习惯是定期审查记忆内容，把过期偏好删掉，把长期规则保留。

第二步：按任务复杂度选择模型与努力级别

作者不建议把 Haiku 当主力，因为 Sonnet 的回答质量提升明显，同时仍然足够快。对于普通办公、研究、写作和轻量分析，Sonnet 往往是默认选择；当任务需要多步骤推理、复杂代码或高风险判断时，再切到更强模型和更高 effort level。反过来，简单改写和短任务用高配模型就是浪费。

这一步的关键不是记住哪个模型最好，而是建立选择规则。你可以把 Claude 看成一组不同成本的计算资源：低风险低成本，高风险高配置。这样既节省额度，也能避免把复杂任务交给不合适的设置。

第三步：用 Projects 固定工作场景

作者说自己大约 90% 的聊天都从 Projects 开始，因为 Project 能让上下文保持在一个边界内。比如你有一个客户项目，就把会议纪要、品牌语气、历史方案、报价模板和待办事项都放进去；以后任何新聊天都不用重新解释背景。

Project 的价值在于减少重复说明，也减少模型误解。它让 Claude 不再面对孤立问题，而是在一个清晰的工作空间里响应。对团队或长期项目来说，这比单次聊天稳定得多。

第四步：把重复流程做成 Skills

Skills 适合那些“每次输入不同，但流程稳定”的工作，例如每周内容包、销售邮件、研究摘要、竞品分析、项目复盘。视频里的例子是餐厅周末特价菜：Claude 先读取菜单，再按既定要求生成网页文案、社交媒体内容、图片提示词和邮件文案。下次只需要换菜单，流程本身不用重写。

这和普通 prompt 的区别在于，Skill 可以包含更完整的步骤、规则和产出格式。它更接近一份内部 SOP。对于专业用户来说，真正提高效率的不是“会写一个好 prompt”，而是把高频工作做成可重复、可审查、可持续改进的技能。

第五步：通过 Connectors 接入真实资料和工具

连接器让 Claude 读取或操作外部服务，例如 Gmail、Calendar、Google Drive、会议记录工具或图像/视频生成服务。作者强调连接器不只是“多一个插件”，而是让 Claude 快速获得真实上下文：邮件里有客户沟通方式，日历里有日程，Drive 里有文件，会议记录里有决策。

但连接器也意味着权限边界。实操上应该只连接当前任务需要的服务，并尽量让 Claude 先分析、草拟和建议，再由人确认关键操作。把连接器看成上下文入口和工具入口，而不是放弃审查的理由。

第六步：用 Co-work 和 Claude Code 分流任务

视频后半段把 Co-work 和 Code 做了清晰区分：Co-work 像助手，适合仪表盘、项目规划、内容流水线、定时任务和长期工作；Claude Code 像工程师，适合写应用、网站、自动化脚本、Chrome 扩展和生产力工具。二者都属于更强的 Agentic 用法，但承担的任务类型不同。

作者还提到 Co-work 的 scheduled tasks：你可以让某个 Skill 每周五早上自动运行，醒来时内容包已经准备好。Claude Code 则更适合在本地桌面使用，直接指定文件夹，让它在真实项目目录中创建、编辑和组织文件。这里的重点是，不要把所有事都塞进聊天框；不同任务应该进入不同运行环境。

05引用块：这期最值得记住的工作方式

第一次回答通常不是终点。把 Claude 当成协作者，不断追问漏洞、改进点、遗漏和反例，输出质量会明显提高。

视频里有一个很实用的态度转变：不要默认 Claude 第一次就对，也不要只把它当成听话的执行器。更好的用法是让它暴露自己的不确定性，要求它找出你的思路漏洞，也要求它找出自己回答里的薄弱环节。这种“推回去再迭代”的习惯，比背 prompt 模板更重要。

Co-work 更像助手，Claude Code 更像工程师。前者适合持续工作流，后者适合真实代码和文件系统。

这句话能帮助你避免工具错配。内容排期、资料整理、定时任务和项目仪表盘可以交给 Co-work；真正要写应用、改文件、搭自动化，应该进入 Claude Code，并配合 Git、测试和审查流程。
