一、问题引入：为什么大家突然开始谈 Harness

过去一年，AI 编程工具的讨论经常停留在模型本身：哪一个模型更会写代码、哪一个上下文更长、哪一个 benchmark 更高。但视频里的关键判断是，模型只是一半的智能，另一半来自围绕模型搭建的 harness：它负责组织工具、文件系统、终端、记忆、沙箱、子任务、UI 和可观察性。

DeepSeek Harness 的看点就在这里。它不是又一个聊天窗口，而是一个把 Coding Agent 拆成插件化零件的开发者预览版。视频中反复强调「everything is a plugin」：模型、工具、技能、会话、沙箱、文件系统、Agent loop、编排层，甚至 UI 都可以被替换或扩展。这个方向与 Claude Code、OpenAI Codex、OpenCode、Cursor Agent 的竞争点非常接近，但它把可替换性放到了产品结构的中心。

因此，这期视频值得看的不是「它是不是某个工具的杀手」这种标题式判断，而是它提供了一个工程视角：如果你要让 Coding Agent 进入真实项目，必须关心的不只是回答质量，还包括运行轨迹能否追踪、工具调用能否审计、插件能否隔离、上下文能否复用，以及失败后能否从中间状态恢复。

二、核心概念解释：Harness 不是模型，而是模型的工作系统

1. Harness 的职责

在视频语境里，Harness 可以理解为「把模型变成开发同事的运行时」。裸模型只能输入文本、输出文本；Harness 则把它接到真实工作环境：读取文件、运行命令、调用工具、保存状态、拆分子任务、查看历史、继续或回放一次执行过程。对于编程 Agent 来说，这些外部能力决定了它能不能处理多文件修改、调试循环和长任务。

2. 插件化为什么重要

传统 IDE 插件通常增强的是人的编辑器体验；DeepSeek Harness 这类系统里的插件增强的是 Agent 的行动能力。视频提到模型、工具、技能、沙箱、记忆都可插拔，意味着团队可以选择不同模型供应商、替换工具权限、按项目放入专属技能，也可以为安全审查或代码评审做专门插件。

3. Trajectory 是可调试性的关键

视频中最值得工程团队注意的是 trajectory view。它不只显示最终聊天消息，而是记录 Agent 在任务中做过什么：用户输入、上下文、助手响应、工具调用、终端结果、子 Agent、补充上下文。这样一次执行就不再是黑盒，你可以搜索、恢复、fork 到早期节点，或者复盘为什么某个工具调用把任务带偏。

视频中的核心判断可以转述为：模型本身只是智能的一半，真正把模型能力释放出来的是围绕它的 Harness。

4. 早期预览版应该怎样看

视频把它称为 developer preview，并展示了 NPX 启动、模型选择、工作区选择、插件安装、轨迹检查等功能。这里最合理的态度是：把它当成可以学习架构方向和实验流程的早期工具，而不是直接替换成熟生产环境。越是强调插件生态，越要先看权限、来源、执行边界和审计能力。

三、关键论点与实操步骤

步骤 1：用 NPX 快速启动，而不是先配置复杂工程

视频首先演示的是低门槛启动：准备 Node.js，然后在一个干净项目目录中执行 NPX 命令。它的设计目标是让开发者不用先克隆大量样板代码，也不用理解内部框架，就能进入一个可运行的 Harness UI。对新工具评估来说，这很重要，因为你应该先用隔离目录试跑，再决定是否把它接入真实仓库。

步骤 2：选择模型与 provider，把「智能」和「壳」分开评估

视频提到可以在 Harness 中选择不同模型和 provider，例如把 DeepSeek 新模型接进来，也可以调整 reasoning 强度。这里的工程含义是：不要把模型能力和 Harness 能力混在一起比较。一个任务成功，可能来自模型更强；一个任务失败，也可能是工具权限、上下文组织或执行循环不够稳。拆开看，才知道该换模型还是该改工作流。

步骤 3：用工作区隔离任务范围

演示里会选择一个 workspace，然后描述要构建的东西，例如 3D mechanical clock simulation、gear、escapement、pendulum、clock hands 等。对 Agent 工程来说，工作区边界就是安全边界和上下文边界。你给它一个空目录，它会像脚手架生成器；你给它一个真实仓库，它就可能修改现有代码。两种模式应该分开测试。

步骤 4：观察工具调用，而不是只看最终页面

视频展示 Agent 在 canvas 中思考、调用工具、运行命令、执行任务。这里不要只被 demo 的视觉效果吸引。真正需要记录的是：它是否先理解目标、是否分解任务、是否能在失败后读取错误、是否会重复执行无意义命令、是否留下可审计轨迹。这些比一次 demo 是否生成酷炫 3D 效果更能说明工具成熟度。

步骤 5：进入 trajectory 复盘上下文和工具结果

Trajectory view 的价值在长任务中会放大。视频说可以看到 user input、context、assistant response、tools used，以及每一步发生了什么。对团队使用来说，这相当于 Agent 的执行日志和审计链。代码 review 时，你不只 review diff，还要 review Agent 是通过什么资料、什么命令、什么假设得到这个 diff 的。

步骤 6：谨慎安装第三方插件

视频后半段提到插件市场、设计插件、Webline Access 这类把本地 UI 暴露到网络中的扩展，同时提醒插件未必都经过验证。这里必须把安全放在前面：任何能读取仓库、访问终端、暴露本地服务或转发网络请求的插件，都应视作高权限代码。先看源代码、权限说明、维护者和更新频率，再决定是否安装。

五、引用块：这期视频真正有价值的判断

如果把 Coding Agent 当成系统来设计，模型只是推理核心；文件、工具、会话、沙箱、轨迹和插件，才决定它能不能进入真实工程流程。

这句话可以作为评估所有 AI 编程工具的底层问题。一个工具再会生成代码，如果不能解释自己做了什么、不能限制权限、不能恢复执行轨迹、不能让团队复用规则，就很难从个人 demo 进入工程制度。DeepSeek Harness 的早期意义不是证明谁会替代谁，而是把「Harness Engineering」这个方向又往前推了一步。
