在云端并行运行多个 AI Agent：Warp Oz 工作流拆解

How I'm Using AI Agents in 2026

Tech With Tim 22:56 32,275 views Warp · Oz · Cloud Agents

一、问题引入：从“一个本地 Agent”到“一组云端工人”

这支视频的核心不是介绍一个更聪明的聊天框，而是把开发者正在经历的瓶颈讲清楚：当一个任务只需要修一处代码，本地运行一个 Agent 就够了；但当任务要同时拆成前端、后端、测试、代码审查、PR 处理和外部触发时，一个 Agent 顺序跑就会变成新的排队系统。

Tech With Tim 用 Warp 的 Oz Agent 平台做演示，目标是把多个 AI Agent 放到云端并行运行。视频开头明确给出使用场景：同时启动 5、10、15 甚至 20 个 Agent，让它们在不同环境中处理复杂开发任务，或在每个 Pull Request、Slack 消息、Linear 任务触发时自动运行。

值得看的地方在于，它没有停留在“AI Agent 很强”的口号，而是把一套完整工程链条串起来：创建项目目录、连接 GitHub、准备云端环境、拆分计划文件、创建可复用 skill、并行启动 Agent、生成 PR，再让 GitHub Actions 调用 Agent 做代码审查。

二、核心概念解释：这套系统真正管理的是什么

1. Warp 不只是终端，而是 Agentic Development Environment

视频里对 Warp 的定位很关键：它“看起来像终端”，但更准确地说是一个围绕命令、文件、Agent 会话和云端环境组织起来的开发界面。传统 IDE 把注意力放在代码编辑器；Warp 的假设是，AI 时代的人类开发者越来越多地在终端里调度命令、运行服务、启动容器、查看日志和指挥 Agent。

因此，Warp 把自然语言和 shell 命令放在同一入口：你可以输入 ls 这类标准命令，也可以输入“创建一个目录并打开它”这样的自然语言任务。工具会判断这是命令还是 Agent 指令，并把结果反馈到同一个工作流里。

2. Oz 是可从 UI、CLI 和第三方触发的 Agent 平台

Oz 在视频中承担的是“Agent 运行平台”的角色。它可以在 Warp 内部打开，也可以通过 oz.warp.dev 的 dashboard 管理，还可以由 CLI 或外部系统触发。每次运行都有状态、环境、会话入口，甚至可以 SSH 进去接管或修正云端 Agent 的行为。

这个设计把 Agent 从“我电脑上的一次聊天”提升为“可观察、可调度、可重复运行的任务单元”。如果你希望 Agent 在你合上电脑后仍继续工作，或者希望 PR 创建后自动触发审查，这种云端运行模型才有意义。

3. Environment、Skill、Integration 是三块积木

视频反复出现三个对象：环境、技能和集成。环境决定 Agent 在哪里运行，通常包含 Docker image、初始化命令、关联仓库和依赖配置；Skill 是可重复执行的任务说明，比如“前端开发”“后端开发”“验证测试”；Integration 负责把 Agent 接到 GitHub、Slack、Linear 或 API 触发器上。

这三个概念合在一起，才构成工程上可扩展的 Agent 系统：环境保证可复现，Skill 保证任务边界，Integration 保证它能进入真实团队流程。

三、关键论点 / 实操步骤

步骤 1：先把项目变成可被 Agent 接手的仓库

演示从一个空目录开始。Tim 先让 Warp 创建名为 YouTube agent demo 的目录，然后在这个目录中初始化一个简单应用。这个阶段并不急着并行，而是先让本地 Agent 搭出前端、后端、基础文件和初始代码。

接着，他要求 Agent 创建 GitHub 仓库、设置远程仓库并提交现有更改。这里的工程理由很直接：云端 Agent 需要从远程仓库拉取代码，也需要通过 Pull Request 把结果交回主分支。如果代码只在本机目录里，云端并行就没有稳定的协作媒介。

步骤 2：为云端 Agent 创建可复现环境

视频在 9 分钟左右进入环境创建。环境可以通过 guided setup 创建，也可以在 UI 里指定 Docker image、setup commands、关联 GitHub repository 等参数。这里最重要的不是界面按钮，而是“把 Agent 会在哪个系统里运行”显式化。

没有环境，Agent 只能猜测依赖；有了环境，它可以在一致的容器中安装包、运行测试、启动服务并访问指定仓库。对于多 Agent 并行，环境尤其关键，因为每个 Agent 都应该在隔离但相同的基础条件下工作。

步骤 3：用计划文件拆成前端、后端、测试三条任务线

视频的中段是最像真实团队流程的部分：Tim 先让一个本地 Agent 生成总体计划，并把任务拆成三个 markdown 文件，分别描述前端、后端和测试需要完成什么。这一步避免了“直接启动三个 Agent，各做各的”导致的目标不一致。

更好的理解方式是：计划文件就是多 Agent 协作的接口。它不只是提示词，而是任务契约，明确每个 Agent 的范围、输入、验收目标和交付物。并行不是把混乱放大，而是先把依赖和边界写清楚，再让不同执行者各自推进。

步骤 4：把计划封装成 Skill，再用 oz agent runcloud 并行启动

随后 Tim 创建三个 Skill，对应前端、后端、测试三个计划。Skill 在这里表示可重复调用的任务能力，不必每次重新写长提示。视频中提到的 oz agent runcloud 是关键命令：它能指定模型、Skill、环境等参数，在云端启动 Agent。

实际意义是，开发者不再只是在聊天窗口里等待一个 Agent 完成所有事，而是把工作拆成多个独立执行单元，让它们并行生成 PR。这样做的收益来自并行度和清晰职责，不是来自某个单体 Agent 变得更聪明。

步骤 5：进入云端会话观察、接管和纠偏

视频还展示了一个容易被忽略的能力：你可以打开某个正在运行的 Agent 会话，直接查看它的状态，甚至通过 Warp 或浏览器进入 session 进行 steering。对于真实工程来说，这比“黑盒等待结果”重要得多。

Agent 一旦能改代码、推分支和创建 PR，就必须有观察与干预入口。否则失败时你只会看到一个坏结果，而不知道它卡在依赖安装、测试失败、权限不足还是需求理解偏差。

步骤 6：用 GitHub Actions 把 Agent 放进代码审查链路

最后一段演示 GitHub Action 集成。Tim 在 Oz UI 中复制预置的 GitHub Action 配置，让仓库在 Pull Request 事件上触发 Agent 做代码审查。随后他补充设置 Warp API key secret，并重新运行 action，确认 Agent 审查流程能够完成。

这部分说明 Agent 工作流不只适合“我手动叫它写代码”，也适合进入 CI/CD 与代码评审过程。它的价值在于把 Agent 变成持续运转的开发基础设施，而不是一次性的写码助手。

四、对比表格 / 决策矩阵

模式 适用场景 优点 风险 / 决策建议

五、引用块

视频里最值得抽象的一点是：当开发任务变复杂，界面中心会从“写代码的编辑器”转向“调度命令、环境和 Agent 的终端”。

这句话不是原文逐字引用，而是对视频核心判断的转述。Tim 的论点是，AI 时代开发者仍然要理解项目结构、环境、命令、仓库和 PR 流程；变化在于，很多执行步骤可以交给多个 Agent 并行完成。

多 Agent 并行不是让一个提示词变长，而是把任务拆成可以独立交付、独立验证、独立合并的工程单元。

这也是这支视频区别于普通工具介绍的地方。它实际演示了“计划 → Skill → 云端运行 → PR → Action 审查”的完整闭环。
