Model Context Protocol

MCP 到底如何工作：给 AI 应用开发者的协议拆解

How Model Context Protocol (MCP) actually works

Google Cloud Tech 7 分 58 秒 约 275,146 次观看 字幕整理

01问题引入：为什么 AI 调工具总是很脆

这支短视频解决的不是“MCP 是什么缩写”这种表层问题，而是 AI 应用开发里一个非常具体的痛点：模型想要使用日历、数据库、文件系统、搜索引擎或公司内部工具时，开发者往往要为每个系统写一套胶水代码。每个 API 的鉴权、参数、错误语义、速率限制都不同；模型换了、提示词改了、工具版本升级了，连接层就容易断。

视频的核心判断是：传统 API 面向的是确定性程序，而今天的语言模型并不是这种消费者。程序在调用 API 前通常已经知道自己要哪个 endpoint、传哪些字段、拿到什么结构；模型则经常需要先探索、澄清、比较，再决定下一步动作。MCP 的位置就在这里：它把“模型如何发现工具、理解工具、调用工具、接收结果”变成一套可复用协议。

MCP 可以理解为模型与外部系统之间的共享语言：模型不需要预先知道每个 API 的实现细节，也能发现可用能力并发起结构化调用。

所以，MCP 不应该被理解成一个替代 REST、GraphQL 或数据库驱动的新后端协议。更准确的说法是：它把已有系统包装成模型友好的界面，让 Agent 不再靠超长系统提示词硬记一堆工具说明，而是通过统一 schema 动态理解环境。

02核心概念：MCP 是模型的“外部能力目录”

视频把 MCP 定义为一种开放标准，用来把模型连接到工具、数据和上下文。这个定义里有三个关键词：连接、标准、上下文。连接意味着它关心的不只是函数调用，还包括数据读取、资源枚举、提示模板和执行结果；标准意味着不同服务可以用同一种方式暴露能力；上下文意味着模型调用工具前后都需要能把外部信息纳入推理。

Client：发起任务的一侧

MCP client 通常是语言模型所在的应用、Agent 框架或 IDE 助手。它代表模型去问：“你这里有哪些资源？有哪些工具？这些工具需要什么输入？调用后会返回什么？”这让 client 不必为每个工具写死专属逻辑，而是可以通过协议拿到可发现、可解释、可验证的能力清单。

Server：暴露能力的一侧

MCP server 则是把真实世界系统包装出来的一层。它可以在后面连接数据库、企业文档、CRM、日历、邮件、搜索服务或文件系统。模型看不到内部 REST endpoint 或 SQL 查询，只看到 server 按 MCP schema 公开的 tools、resources、prompts 和上下文信息。

一次连接不是“返回数据”，而是“声明能力”

传统集成经常是“调用某个接口，拿回某份数据”。MCP 的第一步更像是握手：server 先声明自己支持什么、有哪些资源、哪些动作可执行、每个动作要求什么输入。这个能力广告是协议价值的核心，因为模型可以据此决定下一步，而不是依赖开发者把所有可能操作提前写进提示词。

对开发者来说，MCP 最值得抓住的一点是“发现优先”。一个设计良好的 server 不只是把函数暴露出去，还要让模型知道这个函数适合何时使用、参数边界在哪里、输出会产生什么副作用。

03关键论点与实操步骤

第一步：把能力拆成 tools、resources、prompts 和 context

视频列出 MCP 中最常见的资源类型：tools、resources、prompts 和 context。Tools 是模型可以主动调用的动作，例如搜索数据库、发送邮件、分析文件；resources 是可读取的数据和状态，例如文档、数据库行、图片或日志；prompts 是可复用的任务模板；context 则是模型在推理时需要拉入的外部信息，例如最近对话、公司数据或用户偏好。

这四类对象的区别很重要。很多失败的 Agent 集成会把所有东西都塞成“工具”，导致模型把只读资料也当成动作，把提示词模板也当成 API。更稳的做法是先判断：这个对象是可执行动作、可读取状态、可复用指令，还是运行时上下文？分类清楚后，模型更容易选择正确的交互方式。

第二步：让每个能力携带机器可读元数据

视频强调，每个工具或资源都要带上描述它做什么、期望什么输入、返回什么输出的 metadata。这相当于把“人类读 README 才懂的接口说明”变成模型可消费的结构化契约。对 Agent 系统来说，这比把几十段工具文档塞进 system prompt 更稳定，也更容易做验证。

例如，一个“发送邮件”工具不只需要名字，还要明确收件人、主题、正文、是否允许外发、是否需要确认；一个“查询会议记录”的 resource 不只需要 URL，还要说明权限、时间范围和返回格式。协议本身不能替你设计产品边界，但它迫使你把边界写到模型能理解的位置。

第三步：把旧 API 包到 MCP server 后面

视频对“为什么有 API 还要 MCP”的回答很直接：API 是给人写的程序用的，MCP 是给模型用的。底层仍然可以是 REST、GraphQL、SQL 或内部 RPC，只是模型不用直接接触这些细节。MCP server 负责把底层系统翻译成统一的工具声明、资源声明和调用结果。

这意味着迁移 MCP 不一定要重写系统。更实际的路线是选一个高频、低风险的能力先包装，例如只读文档搜索、日历查询、issue 检索或指标查询。等发现、权限、错误处理都稳定后，再把带副作用的工具逐步加入，例如创建 ticket、发邮件、修改文件或触发部署。

第四步：让 Agent 编排多个 server

视频举了个人助理例子：旧方式要分别集成 Google Calendar、Notion、Gmail，处理每个服务的鉴权和边界，再用长提示词教模型怎么调。MCP 方式则是接入 calendar server、notes server、email server，每个 server 各自声明能力。模型可以先列事件，再读取会议摘要，最后草拟跟进邮件。

这里的关键不是“少写几行 API 调用”，而是编排方式变化了。开发者仍要负责权限、审计和错误恢复，但模型可以用同一种协议理解多个系统，决定数据怎样在工具之间传递。这正是 Agent 从单工具 demo 走向工作流系统时最需要的抽象。

04对比表格：API、函数调用与 MCP 怎么选

方案 适用场景 优点 风险 决策建议
直接调用 API 业务逻辑固定，调用方是确定性程序，endpoint 和参数长期稳定。 路径短、性能可控、调试工具成熟，适合传统后端服务。 模型需要靠提示词记住接口细节，工具多了以后上下文和维护成本迅速上升。 如果没有 LLM/Agent 参与决策，继续用 API；不要为了赶潮流强行套 MCP。
模型函数调用 少量工具、单应用内部、工具 schema 可以直接随模型请求下发。 接入快，适合 prototype 和产品内置小工具。 跨应用复用弱，多个客户端共享同一批工具时容易复制 schema 和权限逻辑。 工具数量少且只服务一个模型入口时足够；当工具需要跨客户端复用时再升级。
MCP server 一个外部系统要服务多个模型客户端，或需要动态发现 tools/resources/prompts。 统一发现、统一 schema、统一调用语义，便于把已有系统模型友好化。 server 设计不好会把后端复杂度原样暴露给模型，权限和副作用治理仍需额外工程。 优先用于高复用工具、企业数据入口、IDE/Agent 工作台和跨服务编排。
完整 Agent 平台 需要计划、记忆、多步执行、任务恢复、权限审批和观测闭环。 把 MCP 作为工具层的一部分，能承载真实业务流程。 复杂度最高，必须处理失败重试、审计、人工确认和状态一致性。 不要一开始就平台化；先用 MCP server 稳住工具边界，再逐步加入编排能力。

05引用块：这支视频最值得记住的判断

API 仍然存在，MCP 只是把它们变得更适合模型使用：发现、验证和执行都放进统一结构里。

这句话背后的工程含义是：MCP 不会自动让系统安全，也不会自动让 Agent 聪明。它做的是把模型与工具之间最容易散落在提示词、README、胶水代码里的协议部分收拢起来。真正上线时，你仍然要回答鉴权、确认、回滚、审计、速率限制、敏感数据脱敏等问题。

但这不削弱 MCP 的价值。相反，它把开发者从“为每个模型和工具组合写专用适配”里解放出来，让团队可以把精力放在更重要的地方：哪些能力应该开放给模型，哪些动作必须人工批准，哪些资源只读，哪些工具可以链式调用。
