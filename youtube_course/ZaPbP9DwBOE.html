不要急着学 AI Agent：先补齐这些基础概念

Don't learn AI Agents without Learning these Fundamentals

KodeKloud 56:39 约 1,019,705 次观看 LLM · RAG · LangGraph · MCP

一、问题引入：Agent 不是第一个概念，而是最后的组合题

这支视频的价值不在于教你背一堆新名词，而是把近几年 AI 工程里反复出现的概念放进一个连续故事：一家公司 TechCorp 有大量内部文档，员工希望直接问“假期能不能请假”“某个政策怎么解释”，系统要能理解问题、找到相关资料、调用模型回答，并把答案限制在可追溯的上下文里。

如果直接从“AI Agent”开始学，很容易把 Agent 理解成一个神秘的黑盒：会规划、会用工具、会自己执行。但视频提醒的是，Agent 的能力来自更底层的积木。上下文窗口解释模型怎样临时记住输入，Token 解释成本和长度限制，Embedding 和向量数据库解释怎样按语义检索，RAG 解释怎样把检索结果送回模型，LangChain / LangGraph 解释怎样组织调用链和工作流，MCP 则解释工具如何被标准化暴露给模型使用。

因此，这门课更像一张路线图：先理解模型如何接收信息，再理解知识如何被编码和检索，最后才讨论怎样把工具、流程和外部服务接进一个可运行的 Agent。对工程师来说，这比“十分钟做一个 Agent demo”更有阅读价值，因为它能帮助你判断一个系统哪里该用检索，哪里该用工作流，哪里只是 prompt 还没写清楚。

真正的 Agent 并不是单个魔法组件，而是上下文、检索、工作流和工具协议组合后的工程系统。

二、核心概念解释：从模型输入到外部工具

1. LLM 与上下文窗口：模型只知道你给它的现场

视频先从大语言模型讲起。常见模型如 GPT、Claude、Gemini 都可以被看成经过海量 token 训练的 Transformer 系统。训练数据覆盖很多公共领域，但它天然不知道 TechCorp 的 500GB 内部文档。要让模型回答公司内部问题，就必须把相关内容放进当前请求，或者通过外部系统检索后再喂给模型。

这里引出上下文窗口。上下文窗口是一次对话中模型能看到的“短期记忆”，通常以 token 衡量。它很有用，但不是无限知识库：窗口越长，成本越高，干扰也越多；把整本文档硬塞进去，既浪费 token，也可能让模型在长上下文里忽略真正关键的段落。

2. Token 与成本：工程上不能只看“能不能回答”

视频中的 API lab 强调了 token 使用量：prompt token 是你输入的内容，completion token 是模型输出的内容，total token 是两者之和。输出 token 往往更贵，因此“让模型多写一点”不是免费行为。实际工程里，检索、摘要、上下文压缩、引用控制，本质上都是在质量和成本之间做设计。

3. Embedding：把文本从“字面值”转成“意义空间”

传统 SQL 更擅长按字段和值查询。比如文档里写的是 holiday，而用户问 vacation，字面匹配可能找不到。Embedding 的作用是把句子转成高维向量，让意思相近的词和句子在向量空间中距离更近。这样用户问“我能不能在节假日请假”，系统可以找回包含“holiday policy”的段落，而不要求用户猜对关键词。

4. Vector DB 与 RAG：先找资料，再让模型作答

向量数据库负责存储 embedding，并按语义相似度找回相关 chunk。RAG 的完整流程是：把文档切块，生成 embedding，写入向量库；用户提问时，也把问题转成 embedding；检索 top-k 相关段落；把这些段落放入 prompt；最后让 LLM 根据这些上下文回答。视频特别强调 prompt 中要明确要求“只基于已提供文档回答”，这能降低幻觉，并让答案附带来源。

5. LangChain、LangGraph 与 MCP：从调用库到可编排系统

当系统从单次 API 调用升级成多步骤流程时，抽象层就变得重要。LangChain 提供统一接口，减少在 OpenAI、Gemini、Grok 等 provider 间切换的样板代码。LangGraph 则更适合表达带状态、带分支、可循环的工作流，例如先检索，再判断是否需要工具，再生成答案。MCP 的角色更像工具协议：服务器暴露工具和 schema，Agent 通过统一方式发现并调用计算器、天气服务、数据库或文件系统。

三、关键论点与实操步骤：把 TechCorp 问答系统搭起来

步骤一：先能稳定调用模型，而不是先追 Agent 框架

视频里的第一组 lab 从最普通的 API 调用开始：验证环境、配置 API key 和 base URL、发出请求、解析返回对象。重点不是某个 SDK 的语法，而是训练你看懂模型响应结构。很多初学者在 Agent 框架里迷路，是因为连响应里的 content、usage、prompt tokens、completion tokens 还没搞清楚。

步骤二：用 LangChain 降低 provider 切换成本

当你已经理解一次模型调用后，LangChain 的价值才清晰：它把多家模型供应商包装成接近一致的接口。视频对比了传统 SDK 调用和 LangChain 调用，前者需要较多 boilerplate，后者通常改模型名或 provider 配置就能切换。这对企业系统很现实，因为模型选择常随成本、延迟、区域合规和效果评测变化。

步骤三：把文档切成有意义的 chunk

RAG 不是“把 PDF 扔进向量库”这么简单。视频提到从固定字符切分升级为基于段落、带 overlap 的切分策略。原因是 chunk 必须保留完整语义：太短会丢上下文，太长会引入噪声；没有 overlap，跨段落的概念容易断裂。一个好的 chunk 策略，决定了检索结果能不能让模型生成可靠答案。

步骤四：建立向量库并选择 embedding 模型

在 lab 中，系统用 ChromaDB 之类的向量库建立 TechCorp RAG collection，并配置 embedding 模型。这个步骤相当于给公司文档建立语义索引。索引一旦建好，用户问题就不再只按关键词查找，而是按语义相似度找回候选段落。

步骤五：把检索结果写进结构化 prompt

视频中的 RAG prompt 有一个关键约束：答案必须来自检索到的文档；如果上下文没有信息，就明确说没有相关资料。这个设计看似简单，却是企业场景的核心护栏。没有这条约束，模型会倾向于用常识补全答案；有了它，系统才更接近可审计的知识库问答。

步骤六：用 LangGraph 表达多步 Agent 工作流

当问答流程需要条件判断时，LangGraph 的价值出现了。例如一个节点负责接收问题，一个节点负责检索，一个节点负责生成答案，一个节点负责判断答案是否足够或是否需要工具。Graph 不只是“把函数串起来”，它让状态、边和分支都变成显式结构，方便测试、调试和扩展。

步骤七：用 MCP 接入外部工具

MCP 部分用计算器和天气服务作为示例：MCP server 暴露工具及 schema，Agent 通过 client 读取工具列表，再在需要时调用。视频把 MCP 类比为 USB：协议像接口，server 像设备，tool 是设备功能，LangGraph Agent 是使用这些功能的电脑。这个类比对初学者很有帮助，因为它把“工具调用”从框架私有能力变成标准协议问题。

五、引用块：视频里最值得带走的判断

如果你还没理解 context window、embedding、vector database 和 RAG，就直接学习 Agent，很容易只学到框架表面，而不知道系统为什么能工作。

这句话可以转化成一个工程判断：Agent 开发不是“选一个框架然后堆工具”，而是先把问题拆成信息输入、知识检索、模型推理、工具执行和结果校验几个层次。每一层都有自己的失败模式。上下文太乱会让模型跑偏，检索太弱会找不到证据，prompt 太松会制造幻觉，工具协议没有权限边界会带来安全问题。

所以这支视频适合两类人：一类是刚开始学习 Agent 的开发者，需要建立概念地图；另一类是已经做过 RAG 或工具调用 demo 的工程师，需要回头检查自己的系统是否有明确的数据流、状态流和责任边界。
