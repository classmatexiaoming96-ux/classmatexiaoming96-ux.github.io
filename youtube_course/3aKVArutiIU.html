10 分钟掌握 Claude Code 的 80%：七层能力金字塔

一、问题引入：Claude Code 不是“更聪明的聊天框”

这支视频的节奏很快，但它真正讲的不是一堆炫技命令，而是如何把 Claude Code 当成一个能参与软件工程流程的 AI teammate。作者开场给出一个很激进的判断：Claude Code 可以让没有太多经验的人更快完成计划、编码、测试和部署。这个说法当然有营销味，但拆开看，它背后的实践逻辑是成立的：如果你只把 Claude Code 当问答框，它最多帮你解释代码；如果你把它放进项目规则、模型路由、调试反馈和协作流程里，它才开始像一个可管理的工程成员。

视频用“七层金字塔”组织内容，适合初学者按层补齐能力。第一层是安装和启动，第二层是根据任务选择模型，第三层是通过项目规则把 Claude 变成长期队友，第四层是用截图和代码上下文调试 UI，第五层是队列化任务，第六层是 plan mode、think hard、ultrathink 与 subagents，最后一层是把 Claude Code 接到 GitHub 协作里。

可以把整支视频的核心转述成一句话：不要把 Claude Code 当临时顾问，要把它放进你的工程制度里，让它按规则、按阶段、按任务深度工作。

二、核心概念解释：七层金字塔分别解决什么问题

如果按视频顺序理解，七层不是功能清单，而是从“能打开 Claude Code”到“能管理一组 AI agent”的成长路线。前几层让你能启动和约束工具，中间几层让你能把它放进日常编码，最后几层则让你开始像技术负责人一样拆任务、验收输出、组织协作。

1. Foundation：先让 Claude Code 进入你的工作目录

作者展示了从 Claude 官网复制安装命令、在终端输入 claude 启动会话，也提到可以使用桌面端或 IDE 集成。这里的重点不是安装本身，而是运行位置：Claude Code 应该在你的项目目录里工作，因为它需要读取代码、理解文件结构、生成补丁和运行命令。离开项目上下文，它就退化成普通聊天。

2. Pick your AI teammate：模型选择是工作分配

视频把 Opus 类比成擅长规划和处理模糊任务的资深工程师，把 Sonnet 类比成执行速度更快、适合落代码的工程师。这个比喻很实用：不要所有任务都用同一种模型。需求澄清、架构拆解、风险判断更适合深度模型；按已有计划改文件、补测试、批量执行则更适合速度模型。模型选择本质上是任务分工。

3. AI team rules：项目规则让 AI 形成稳定习惯

作者建议在仓库里维护类似 CLAUDE.md 的规则文件，用来说明分支策略、commit 风格、代码规范、测试要求和函数说明习惯。这个文件会在 Claude 进入项目时被读取，相当于给 AI teammate 的入职手册。规则越具体，输出越稳定；规则越含糊，AI 越容易每次换一种风格。

4. Reusable prompts：把高频要求沉淀成文件

视频还提到把常用提示放进 prompt.md，例如“生成 UI 组件时必须补功能测试、单元测试和 WebDriver 测试”。实际使用时，你可以在 Claude Code 会话里引用这个 prompt 文件，避免每次手写一长段要求。它的价值很朴素：把重复要求从聊天里拿出来，变成项目资产。

三、关键论点与实操步骤：把 Claude Code 放进真实开发循环

视频中段开始从“配置工具”转向“怎么用它工作”。这里有三个特别适合马上实践的点：用截图调试 UI、排队投递任务、在写代码前进入 plan mode。它们看似小功能，实际改变的是你和 AI 协作的节奏。

步骤一：用截图把 UI bug 变成可见证据

作者举的例子是 CSS 问题：后端正常、测试通过，但按钮颜色或间距看起来不对。传统做法是自己翻样式或搜索 Stack Overflow；Claude Code 的做法是把截图贴进去，并明确说“把这个按钮改成蓝色”或“修复这个视觉问题”。因为 Claude 同时能看到 UI 证据和代码库，它可以把现象和实现联系起来，比纯文字描述更准确。

步骤二：不要等一个任务结束才说下一个任务

视频强调 Claude Code 的消息队列能力：当它还在执行“重构 bug 列表支持过滤”时，你可以继续排队“更新 API 文档”和“补两个集成测试”。这不是让 AI 乱跑，而是让你把已经想清楚的小任务顺序投递出去。这样你可以把注意力从等待输出转到设计、验收和后续拆解。

步骤三：用 plan mode 降低“直接开写”的风险

作者认为 plan mode 是 Claude Code 最强的功能之一。进入 plan mode 后，Claude 不会立刻改代码，而是先分析需求、拆结构、提出方案。简单任务可以正常问；中等复杂任务可以要求 think hard，让它考虑边界条件和性能取舍；高风险任务则可以要求 ultrathink，让它用更谨慎的推理方式处理。

步骤四：用 subagents 模拟多名工程师给方案

视频最后把 subagents 放进“高级层”。作者的观点是：真实软件团队会让多个工程师从不同角度看同一个任务，再由技术负责人决定采用哪套方案。Claude Code 的 subagents 可以模拟这种流程：让多个 agent 独立计划，再由你选择；实现时再按后端、前端、测试等边界拆给不同 agent。人的角色从“亲手写每一行”变成“定义任务、审查结果、控制质量”。

落地提醒：任务队列和 subagents 都会放大你的指令质量。任务拆得清楚，它们像流水线；任务拆得含糊，它们会把含糊变成更多含糊。

五、引用块：视频里最值得保留的工作观

“Opus 更像负责规划的资深工程师，Sonnet 更像负责快速交付的工程师。”

这句话之所以重要，是因为它把模型选择从“哪个更聪明”改成了“哪个更适合当前工位”。很多 AI 编程失败并不是模型不够强，而是工作阶段没有分清：你让执行模型做模糊架构判断，或者让深度模型做大量机械修改，都会感觉不顺。正确的节奏是先让模型帮你想清楚，再让模型按计划执行，最后再用测试和 review 收口。

“软件工程师会越来越像管理一组 AI agents 的软件经理。”

这句话听起来有点宏大，但落到日常非常具体：你要会写规则、拆任务、判断模型输出、组织并行工作、做最终验收。Claude Code 降低的是执行摩擦，不会取消工程判断。未来的高杠杆开发者，可能不是键盘敲得最快的人，而是最会把问题拆成可验证任务的人。

七、落地建议：给初学者的一周练习路线

第一天只做安装和熟悉终端会话：找一个小项目，让 Claude Code 解释目录结构、列出入口文件、跑测试。不要急着让它改大功能。第二天写一份简短的 CLAUDE.md，只放五类稳定规则：代码风格、测试命令、禁止改动区域、commit 风格、遇到不确定时如何提问。

第三天练习模型分工：先让深度模型帮你规划一个小功能，再切到执行模型实现。第四天练习截图调试：故意制造一个 UI 问题，提供截图、复现步骤和期望效果。第五天练习任务队列：把“改功能、补文档、补测试”排成三个低耦合任务，让 Claude 依次完成。第六天练习 plan mode：选择一个需要跨文件修改的问题，只让它计划，不让它写代码，然后你审计划。第七天再尝试 subagents，让多个只读 agent 分别审查风险、测试缺口和代码结构。

这套练习的重点不是把所有功能都用一遍，而是建立一个稳定心智模型：你负责问题定义和验收，Claude Code 负责在清晰边界内探索和执行。边界越清楚，AI teammate 越像 teammate；边界越模糊，它就越像一个热心但容易跑偏的临时帮手。
