Building AI Agents in Pure Python - Beginner Course

一、问题引入：为什么要先用纯 Python 写一遍 Agent

这个视频的价值不在于展示一个更炫的框架，而是把 AI Agent 最小可运行的骨架拆开：一个语言模型、若干工具，以及一个持续决策的循环。很多教程会从 LangChain、CrewAI、AutoGen 或某个现成 SDK 开始，初学者很快能跑出 demo，却不一定知道每一次工具调用为什么发生、工具结果怎样回到模型、上下文为什么会膨胀。

Tech With Tim 的做法更接近“把发动机摆在桌面上”。他先解释模型本质上只是接收文本并生成文本，然后把工具定义成普通 Python 函数，再用一个循环把模型输出、工具调用、工具结果和下一轮模型请求串起来。看完之后，你不一定会抛弃框架，但会更清楚框架替你隐藏了哪些关键状态。

可转述的核心判断：一个 Agent 不神秘，它就是模型、工具和循环；上下文与工具结果必须由开发者显式喂回模型。

二、核心概念解释：模型、工具、循环和消息历史

模型只是“会生成文本的脑”

视频开头强调，模型可以是本地的 Ollama、Docker Model Runner、LM Studio，也可以是 OpenAI、Anthropic 等云端服务。无论来源如何，开发者面对的都是一个 API：把消息传进去，拿到一段结构化响应。模型不自动记得刚才说过什么，它看到的“记忆”来自你传入的消息列表。

工具就是模型可请求的外部动作

工具可以是 MCP server、Web search、第三方 API，也可以只是本地 Python 函数。视频为了教学选择本地函数，因为这样最容易看清楚契约：工具要有名字、参数、描述和返回值；模型提出调用请求，程序负责真正执行。

循环让聊天机器人变成 Agent

如果只发一次请求、收一次回答，那更像普通聊天机器人。Agent 的关键是循环：模型发现缺少信息时请求工具，程序执行工具并把结果作为新消息追加，再次请求模型，直到模型不再要求工具调用并返回最终答案。这个循环既是能力来源，也是风险来源，因为它可能运行很多轮、产生费用，并把错误工具结果继续放大。

上下文工程不是口号，而是消息列表管理

视频里反复指出，消息历史就是上下文窗口的主要内容。系统消息约束身份和边界，用户消息提出任务，assistant 消息记录模型之前说过什么，tool 消息承载工具执行结果。所谓 context engineering，实际就是决定哪些信息应该继续放进这份列表，哪些需要裁剪、摘要或丢弃。

三、关键论点 / 实操步骤：从一次 completion 到可调用工具的 mini-agent

步骤 1：先跑通最小 completion

第一段代码只做一件事：创建客户端，选择模型，把一条用户消息传给 chat completion。它看起来普通，却是后面所有 Agent 行为的底座。模型输出的不是“行动”，而是一个响应对象；开发者要知道如何取出可读文本、如何读取 message、如何判断是否包含 tool calls。

messages = [
    {"role": "user", "content": "Explain what an AI agent is in one sentence."}
]
response = client.chat.completions.create(model="...", messages=messages)
print(response.choices[0].message.content)

这一小段代码的教学意义是：先不要急着写工具。你需要确认模型 API、模型名称、API key 和 message schema 都能正常工作，否则后面循环出错时很难定位问题。

步骤 2：把消息历史显式保存下来

接着，视频把单次请求改成终端聊天循环：读取用户输入，追加到 messages，调用模型，把 assistant 的回复也追加回 messages。这样下一轮请求才会“知道”前面聊过什么。这里的重点不是 Python 语法，而是状态归属：模型无状态，应用层有状态。

这一步也解释了为什么长对话会越来越贵、越来越慢，因为每一轮都可能把越来越长的历史重新发给模型。真实系统通常会加摘要、检索、短期记忆和长期记忆，但它们本质上仍然是在控制传给模型的上下文。

步骤 3：用 JSON schema 描述工具

视频里的工具是 Python 函数，例如读取文件、写文件、列出目录或做简单处理。为了让模型知道怎样调用它们，程序要把工具暴露成 schema：函数名、用途描述、参数名、参数类型、哪些字段必填。描述越清楚，模型越不容易把参数拼错。

这里最容易犯的错是把工具当成“模型自己会执行的能力”。模型只会产生 tool call 结构；真正的权限边界、文件路径检查、异常处理和结果序列化，都在你的 Python 运行时里完成。

步骤 4：识别 tool_calls 并执行真实函数

当模型返回的 message 带有 tool calls 时，程序不能直接把 message.content 当最终答案。视频演示了如何遍历每个 tool call，解析函数名和 JSON 参数，映射到本地 Python 函数，然后捕获异常并把执行结果追加成 tool role 消息。

for tool_call in message.tool_calls:
    args = json.loads(tool_call.function.arguments)
    result = available_tools[tool_call.function.name](**args)
    messages.append({
        "role": "tool",
        "tool_call_id": tool_call.id,
        "content": str(result)
    })

这个片段是整节课最重要的转折点：模型提出意图，程序执行动作，结果回到模型。只有把工具结果放回消息历史，模型才有能力基于真实执行结果继续推理。

步骤 5：把“单次工具调用”升级为 Agent run

最终版本把上述逻辑包成一次 run_agent：每次用户输入触发一个内部 while loop。循环中调用模型，若无工具调用就返回最终文本；若有工具调用就执行并继续。外层 while loop 负责持续接收用户输入，内层 while loop 负责完成一次任务。

这种双层结构很实用：外层管理会话生命周期，内层管理任务生命周期。真实产品还会加入最大轮数、超时、费用预算、可取消信号和工具权限提示，否则一个坏 prompt 或坏工具可能让循环停不下来。

五、引用块：把视频里的判断翻译成工程原则

Agent 的循环不是装饰品。没有循环，模型只能回答；有循环，程序才能在“思考、行动、观察、再思考”之间往返。
工具调用的安全边界不在模型里，而在执行器里。模型可以请求写文件，真正允许写哪里、失败后返回什么，必须由代码决定。
消息历史就是你的上下文账本。少记一步，模型会丢状态；全都保留，系统会变慢、变贵，也更难控制。
